# Build Plan

## Files to create

| File | Responsibility |
| --- | --- |
| `package.json` | Define the Next.js project, required dependencies, and the exact `dev`, `build`, and `test:ci` npm scripts. |
| `tsconfig.json` | Enable strict TypeScript and the `src/` import/layout configuration required by Next.js. |
| `next.config.*` | Minimal Next.js configuration, only if required by the selected Next.js setup. |
| `next-env.d.ts` | Next.js TypeScript type declaration file. |
| `.gitignore` | Exclude generated dependencies and build output. |
| `src/app/layout.tsx` | Root layout; applies the shared global stylesheet and system-font baseline. |
| `src/app/globals.css` | The single global stylesheet for the centered layout, accent color, rounded controls/cards, and consistent spacing. |
| `src/app/page.tsx` | Home page containing a heading and a link to `/checkout`. |
| `src/app/checkout/page.tsx` | Checkout UI that builds a cart with the placeholder user ID `guest` and posts it to `/api/checkout`; displays the returned total or error. |
| `src/app/api/products/route.ts` | `GET /api/products`; returns the three exact hard-coded catalogue products. |
| `src/app/api/checkout/route.ts` | `POST /api/checkout`; parses and validates carts, calculates server-side totals, calls the discount stub, and returns the contract response. |
| `src/lib/pricing.ts` | Contains only the exact approved no-op `calculateDiscount` stub specified in the requirements. It becomes human-review-protected after initial creation. |
| `README.md` | Documents installation, scripts, endpoints, validation behavior, in-memory limitation, and request lifecycle. |
| `tests/placeholder.test.ts` | One placeholder unit test executed by `test:ci`. |
| Test-runner configuration file (for example, `vitest.config.ts`) | Minimal configuration needed to run the TypeScript placeholder test outside the Next runtime. |

`package-lock.json` will be generated by `npm install`; it is not application scope.

## Dependencies and scripts

Use a minimal Next.js/App Router stack:

- Runtime: `next`, `react`, `react-dom`
- Development: `typescript`, Next.js type dependencies, and one lightweight TypeScript-capable test runner (for example, Vitest)

Required scripts, with these exact names:

- `dev`: start the Next.js development server.
- `build`: create a production build.
- `test:ci`: run the test runner once in non-watch/CI mode.

No authentication package, database client, external-service SDK, Docker tooling, UI library, Tailwind, or CSS-in-JS dependency will be added.

## Request flow

1. The user visits `/`; the home page links to `/checkout`.
2. The checkout page submits a JSON body to `POST /api/checkout`:
   - `userId: "guest"`
   - a non-empty `items` array containing product IDs and positive integer quantities.
3. The checkout route:
   - handles malformed JSON;
   - validates `userId`, `items`, every `productId`, and every `quantity`;
   - looks up product prices from the server-side catalogue;
   - calculates `subtotal = Σ(unitPrice × quantity)`;
   - calls `calculateDiscount(subtotal)` from `src/lib/pricing.ts`;
   - returns `total = subtotal - discount`.
4. For invalid input, it returns HTTP 400 and `{ "error": "<human-readable message>" }`.
5. For valid input, it returns HTTP 200 and `{ "total": number }`.
6. `GET /api/products` independently returns exactly the required three-product catalogue.

All state remains in process memory; checkout does not create an order record or persist data.

## Tests and acceptance checks

The required placeholder test will be wired to `npm run test:ci`.

Manual/API acceptance checks:

- `npm install && npm run dev` starts successfully.
- `npm run build` completes successfully.
- `GET /api/products` returns exactly three products with the required IDs, names, and floating-point prices.
- A valid checkout with catalogue product IDs and positive integer quantities returns HTTP 200 with the server-calculated `{ "total": number }`.
- Checkout ignores any client-supplied price, if one is included.
- Empty `items`, unknown product IDs, empty/non-string `userId`, missing quantities, zero, negative, and fractional quantities each return HTTP 400 with an error object.
- Malformed JSON returns HTTP 400 with an error object.
- `src/lib/pricing.ts` initially contains only the exact specified stub.
- Home and checkout pages use only global CSS or inline styling and meet the stated visual baseline.

## Constraint coverage

- Next.js App Router, strict TypeScript, and `src/` layout: provided by the project configuration and file structure.
- Product catalogue: server-side and hard-coded in the products route, with exactly three entries.
- Pricing: server-side catalogue lookup only; floating-point dollar values are retained as required.
- Discount extension point: checkout invokes the approved no-op stub without implementing discount logic.
- Sensitive module: no modification to `src/lib/pricing.ts` after its approved initial creation without explicit human approval.
- Scope: only the home page, checkout page, two API routes, pricing module, README, and one test are implemented.
- Styling: one global CSS file, system font, accent color, rounded UI, centered max-width content, consistent spacing.
- Persistence/security: no database, files, authentication, external services, or Docker.

## Assumptions and risks

- The checkout page will present a minimal cart interaction sufficient to submit catalogue items; the requirements do not prescribe exact controls or display behavior.
- Floating-point calculations can exhibit normal binary precision artifacts; the requirements explicitly require this training representation and provide no rounding rule, so no alternative money handling will be introduced.
- The hard-coded catalogue must remain consistent between `GET /api/products` and checkout validation. It should therefore have one server-side source of truth, while preserving the API route responsibilities.
- There is no order ID in the baseline success response; the requirements explicitly state that it is introduced only in a later task.

## Open question

- Should the checkout UI fetch and render the catalogue from `GET /api/products`, or may it offer a fixed minimal cart using known product IDs? The requirements require the API endpoint and a page that posts a cart, but do not specify the UI’s catalogue-loading behavior.
